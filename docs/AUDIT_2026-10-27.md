## Original findings before repair

### 1. P1 — Connection tests bypass Ollama's offline-model checks

**Location:** `desktop_buddy/model_ui.py:534–540`; related guard in `desktop_buddy/providers.py:150–157`.

With **Keep Buddy offline** enabled, the optional connection test calls `Provider.complete()` directly. It never calls `verify_local_model()`, which normal agent tasks use to reject cloud model names and remote-model metadata. Checking that Ollama's HTTP endpoint is loopback does not establish that the selected model runs locally.

**Reproduced:** an Ollama configuration named `fixture-cloud`, pointing only to an isolated loopback fixture, received `POST /api/chat`. The dialog reported “Model connected. Tool calling verified.” Calling the normal local-model check for the same configuration raised “Ollama cloud models are forbidden in local-only mode.” No real cloud inference was made.

**Impact:** the fixed connection-probe prompt can be submitted to a remotely hosted model despite the offline setting. The probe does not include conversation history; this finding is not evidence that normal offline tasks bypass their guard.

**Repair:** enforce the local-model check at the common inference boundary, or explicitly apply it before connection-test inference. Cover both cloud names and remote metadata on otherwise ordinary model names.

### 2. P2 — Messages accepted during finalization can be lost

**Location:** `desktop_buddy/agent.py:254–257`; accepting UI path at `desktop_buddy/ui.py:592–604`.

The final inbox drain happens before the last checkpoint and `done` event. Throughout this interval the worker remains alive, so Send still routes messages into that agent's inbox. `say()` only queues them in memory. The UI clears the composer and displays “Message received,” but no later drain persists these messages. The next task creates a different Agent.

**Reproduced:** paused the final checkpoint with threading events, sent a message while the worker was still alive, then released the checkpoint. The task completed with one stranded inbox message and no corresponding saved message. This uses a controlled scheduling interval, not a probabilistic timing test.

**Impact:** the message appears accepted but disappears on history reload or restart. Attachments submitted in the same interval can also lack a durable transcript reference.

**Repair:** make acceptance and task finalization atomic with respect to the inbox. Persist accepted messages before acknowledging them, and route messages received after the acceptance window closes to a new task or a durable pending queue. Preserve exactly-once transcript insertion.

### 3. P2 — Earlier image results disappear from batched tool calls

**Location:** `desktop_buddy/agent.py:210–212` and `238–246`.

Each tool iteration replaces `last_checkpoint` with a new dictionary containing only turn, pending call, and plan. Images are temporarily accumulated inside that dictionary. The next tool therefore discards images produced by earlier tools before they are appended to the model conversation.

**Reproduced:** a single assistant reply requested `fs.image` followed by `fs.list`. Both tools succeeded, but the next inference request contained zero images and the saved transcript contained zero image references. If the final tool is also an image tool, only that last image survives.

**Impact:** the UI can preview an image that the model never receives. Comparing images or combining a screenshot with another observation silently loses visual evidence.

**Repair:** accumulate images in a separate list for the entire assistant round, then append them after all tool results. Retain every image while preserving tool-call/result ordering.

### 4. P2 — Discarded historical images exhaust the context budget

**Location:** `desktop_buddy/agent.py:193–197`; image removal in `compact()` at `101–103`.

The agent reserves 4,096 tokens for every image in its full in-memory history before compaction. Compaction removes older images from the outgoing request, but that reserved budget is never returned. The original history continues accumulating images across steps and is reconstructed from saved messages on subsequent tasks.

**Reproduced:** repeatedly reading a 2×2 PNG with the default 32,768-token local configuration failed after six inference requests. The error reported only 96 tokens available. At that point compaction retained just two images; the retained transcript with a short diagnostic system message was about 1,400 estimated text tokens. The production system prompt also fits comfortably with those two retained images in the normal input budget.

**Impact:** visual desktop workflows eventually fail with misleading context-limit errors even when the actual retained request would fit. Larger context settings delay the failure rather than correcting the accounting.

**Repair:** budget text and images together using the messages that will actually be transmitted. Recompute image cost as images are omitted; retain the original full transcript separately for persistence.

### 5. P2 — Anthropic thinking choices fail in connection setup

**Location:** `desktop_buddy/model_ui.py:458–468`; working adjustment helper at `desktop_buddy/state.py:135–144`.

The connection dialog assigns the selected thinking budget directly to `reasoning`, then validates it against the unchanged maximum response size. Unlike the main model menu, it does not use `ProviderConfig.set_thinking()` to raise the response limit.

**Reproduced in the native dialog:** with the default maximum response of 4,096 tokens, Low (1,024) succeeds. Medium (4,096), High (8,192), Extra high (16,384), and Maximum (32,768) all fail with “Thinking budget must be at least 1,024 and smaller than the response limit.” The supplied diagnostic also exercises this production configuration method using widget doubles.

**Impact:** users cannot save, use, or test most visible thinking choices during initial Anthropic setup without manually editing advanced response limits. Selecting the same level from the main menu behaves differently.

**Repair:** apply the same thinking/output-limit normalization in setup as in the model menu, after loading the selected protocol and advanced limits, and reflect any automatic limit change in the fields.

### 6. P2 — The advertised desktop test command stops at obsolete UI assertions

**Location:** `scripts/test-model-ui.py:177–178`; additional obsolete picker references at `110–113` and later phases.

`./scripts/run-tests.sh --desktop` fails because `BuddyApp.model_label` no longer exists. The test also references the removed `thinking_selector` and the old model-picker controller/controls. The current interface uses `ModelMenu`.

**Reproduced:** phase 4 raised `AttributeError: 'BuddyApp' object has no attribute 'model_label'`. Because the runner uses `set -e`, it did not execute the remaining native UI, conversation, accessibility, or physical-workflow tests. Those checks were run separately for this audit.

**Impact:** the documented full test command is red, and its model-switching, active-task switching, and stale-discovery scenarios are not reached. Fixing the first attribute assertion alone will not repair the later picker tests.

**Repair:** update the test to exercise the current model menu and its supported interactions, then rerun the complete desktop runner through its final physical-workflow check.

## Scope and limits

Reviewed every production Python module in `desktop_buddy/`, package metadata, source launcher, installer, workflow/test entry points, and relevant security/architecture documentation. Generated build copies were not treated as separate implementations. All findings above are based on local execution or deterministic reproductions.

No live paid provider acceptance was performed. Protocol fixtures cannot establish current model availability, provider acceptance, or end-to-end task quality. No fresh GNOME screen/input permission was requested, no production ComfyUI job was run, and installation/upgrade behavior was reviewed but not reinstalled during this audit. The automated tests use dedicated test profiles; personal history, API keys, and application settings were not inspected or modified.

The runtime repairs, durable-queue schema, regression tests, and updated native model fixture are now in the working tree. The SQLite queue table is created automatically for existing profiles. Restart a running source-checkout app to load the changes; an installed copy must be updated separately. No personal installation or running personal session was replaced.
